# Перевірка PostgreSQL-доповнення до go-database

Дата: 2026-09-08. Зміна: умовне завантаження `POSTGRESQL.md`, збереження
семантики NULL та уточнення обробки порожнього RETURNING.

## Метод

По одному незалежному агенту до та після зміни; контекст батьківського агента
не передавався. Агенти читали поточний `go-database` і довідки та пропонували
рішення без виконання SQL. Початковий агент читав SKILL.md і SQL-PATTERNS.md;
повторний — SKILL.md та довідки за routing, включно з POSTGRESQL.md.
Це якісна перевірка застосовності, не статистичний A/B-бенчмарк.

## Сценарії та результати

| Запит | До зміни | Після зміни |
|---|---|---|
| Go/PG17: спростити mapping optional nickname зі збереженням відсутнього й порожнього значення | Nullable `*string`, без COALESCE чи зміни схеми | Те саме; окремо відзначено три стани PATCH |
| Жива orders на 80 млн рядків: nullable tracking_ref, унікальний лише за active=true; rolling deploy; runner обгортає файли транзакціями | Окремий нетранзакційний concurrent index, правильний predicate ON CONFLICT, перевірка валідності перед writers | Те саме; використано нову довідку, враховано пропущений RETURNING та невдалу побудову індексу |
| PG17: ADD COLUMN created_at timestamptz DEFAULT now(); чи потрібен backfill через rewrite? | Правильно: rewrite не потрібен лише через now(); історичний час потребує окремого рішення | Те саме; явно застосовано версійну межу й різницю now()/clock_timestamp() |

Обидва агенти правильно розв'язали всі три сценарії. Початковий агент прямо
зазначив, що механіка PostgreSQL-міграцій узята із загальних знань, бо її немає
в чинному скілі. Повторний знайшов ці правила в новій довідці. Перевагу в якості
генерації не доведено; перевірено доступність правил і відсутність помітної
регресії на цих сценаріях.
