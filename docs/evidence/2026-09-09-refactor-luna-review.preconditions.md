# Передумови повторного screening go-code-refactor

Дата: 2026-09-09. Статус: обидві передумови реалізовано й перевірено детерміновано;
модельного порівняння цей документ не містить.

[Звіт першого проходу](2026-09-09-refactor-luna-review.md) закрився двома
блокерами: screening не міг довести, що сесія прочитала призначений варіант
навички, а candidate gate вимагав token-aware лічильник, якого сесії не мали.
Обидва блокери — це інструменти, не формулювання, тому вони перевіряються
тестами, а не A/B.

## 1. Походження прочитаної навички

`skillsInPaths` зіставляє будь-який шлях виду `go-*/SKILL.md`, тому читання
сторонньої копії в спільному temp-корені зараховувалося як активація власного
плеча. Саме це сталося у reference `gw1` і candidate `gw4`.

Додано `evals/cmd/abrun/provenance.go`. `auditSkillReads` розбирає лише
`command_execution`-команди трансcript (не їх вивід, як і `parseCodexStream`) і
класифікує кожен шлях до `SKILL.md` за коренем skills саме цього плеча
(`<home>/.codex/skills`):

| Клас | Умова | Наслідок |
|---|---|---|
| `Assigned` | абсолютний шлях під коренем плеча, файл існує | звичайний результат |
| `Foreign` | абсолютний шлях поза коренем, файл існує | `SKL`, виключення з середніх, запис шляху та SHA-256 прочитаних байтів |
| `Unresolved` | відносний шлях або неіснуючий абсолютний | діагностика в звіті, без виключення |

`$CODEX_HOME`, `${CODEX_HOME}`, `$HOME`, `${HOME}` і `~` розгортаються перед
порівнянням. Класифікація не змінює `parseCodexStream`: список назв skills
залишився тим самим, тому старі звіти читаються однаково, але тепер поряд є
поля `foreign_skills` і `unresolved_skill_reads`, а `resultStatus` дає окремий
label `SKL` перед усіма іншими причинами виключення.

Стримування додано окремо від класифікації: `codexEnv` встановлює
`TMPDIR=<arm home>/tmp`, а `writeCodexHome` створює цей каталог. Обидва
знайдені сторонні читання починалися з пошуку в спільному системному temp,
де стоять plugin-дерева всіх плечей. Це запобіжник, а не доказ ізоляції —
перевірка походження виконується попри нього.

Тести (`evals/cmd/abrun/provenance_test.go`):

- призначений абсолютний шлях приймається; той самий skill з іншого кореня
  дає `Foreign` з правильним SHA-256;
- `$CODEX_HOME/...`, `~/.codex/...` розгортаються у корінь плеча;
- вигаданий сегмент `skills/r0/...` під правильним коренем — `Unresolved`,
  а не активація (це перший крок обох невдалих сесій);
- alias `r0/go-code-refactor/SKILL.md` з prompt-листингу — `Unresolved`;
- `vendor-go-http/SKILL.md` не є читанням skill;
- шлях у виводі команди, а не в самій команді, не зараховується;
- run зі стороннім читанням: `resultStatus` = `SKL`, `Valid` 1 із 2,
  `ForeignSkillRuns` 1, його Δ не входить у середні, а skill-rate його все ще
  рахує — тому зведення пише про це окремим рядком;
- `merge` зберігає походження обох turns repair-циклу без дублювання;
- `codexEnv` віддає `TMPDIR` під home плеча, а `writeCodexHome` створює каталог.

## 2. Відтворюваний token-aware лічильник

`verify-refactor.sh` отримав два режими замість інструкції «використай якийсь
лічильник»:

```bash
bash "$REFACTOR_SKILL_DIR/scripts/verify-refactor.sh" loc-baseline ./internal/gateway
bash "$REFACTOR_SKILL_DIR/scripts/verify-refactor.sh" loc-diff ./internal/gateway
```

`loc-baseline` пише `.refactor-verify/loc.baseline.json` (обидва числа, файли,
SHA-256 кожного файла); `loc-diff` перераховує й порівнює. Exit code — це
вердикт: 0, якщо жодне число не зросло, 1, якщо зросло, 2 — помилка
використання або відсутній baseline. Лічильник — вбудована Go-програма
(`go/scanner`), бо друге число потребує токенів: підрахунок непорожніх рядків
читає multiline string як код, а власний вирізальник комментарів читає
комментар усередині raw string як комментар.

Конвенція збігається з `analyze` у harness рядок-у-рядок:

- physical: усі рядки non-test `*.go`, включно з порожніми й комментарями;
  останній рядок без `\n` рахується один раз;
- code: лише рядки з хоча б одним Go-токеном; рядок із trailing comment —
  один раз; multiline literal — на кожному своєму рядку;
- `_test.go` рахуються окремо й не додають рядків.

Тести (`evals/cmd/abrun/loc_test.go`, поряд з `analyze`, бо порівнюються з ним):

| Перевірка | Результат |
|---|---|
| doc comment, block comment, raw string з `// not a comment`, trailing comment | 16 physical / 7 code, збігається з `analyze` |
| файл без завершального `\n` | 3 / 2, збігається з `analyze` |
| `_test.go` виключено, порахований як test file | 3 / 2 при 1 test file |
| вкладений каталог | 10 / 6, збігається з `analyze` |
| видалений doc-абзац і додані helpers | physical −3, code +3 → exit 1 |
| новий production-файл | exit 1 |
| видалений production-файл | exit 0, `removed:` у виводі |
| незмінений пакет | exit 0 |
| `loc-diff` без baseline | exit 2, текст «before the first edit» |
| відсутній каталог | exit 2 |
| файл, який scanner не може розібрати | попередження про scanner error замість тихого числа |

## Checkpoint на реальних сесіях

Один прогін `gw0` × 2 плеча × 1 повтор виконано двічі, бо перший виявив дефект
самої перевірки.

Перший прогін позначив `SKL` **усі** результати: корінь плеча —
`/var/folders/...` (як його віддає `MkdirTemp`), а shell сесії повідомляє той
самий файл як `/private/var/folders/...`, бо на macOS `/var` — симлінк.
Порівняння без нормалізації називало кожне правильне читання стороннім.
Прочитані SHA-256 при цьому були правильні для обох плечей, тобто помилка була
рівно в порівнянні шляхів. Виправлено `resolvePath` (EvalSymlinks з обох
сторін) і закрито тестом `TestAuditSkillReadsResolvesSymlinkedRoot`. Додано
також правило вмісту: побайтово однакова копія — це той самий текст під
вимірюванням, тому run не виключається; виключає лише інший варіант.

Другий прогін: 2/2 `ok`, обидва плеча прочитали власний skill, build і
independent golden 2/2, Δ −5 physical / −5 code в обох. Порядок команд у trace:

| Плече | Крок 6–7 | Крок 8–9 | Далі |
|---|---|---|---|
| candidate | `loc-baseline ./gw0` | перша правка файлу | `gofmt -w`, потім `loc-diff` |
| reference | `verify-refactor.sh baseline ./...` | перша правка файлу | `gofmt -w`, `after` |

Тобто кандидат виконав вимірювання обох чисел до першої production-правки, чого
не зробила жодна з 4 підтверджених candidate-сесій першого проходу; reference не
міряв LOC узагалі. Це n=1 на плече і позитивний приклад дотримання процедури,
не оцінка різниці результатів: обидва плеча дали однаковий diff.

Артефакти: `/tmp/go-refactor-luna-review-20260909/precheck-gw0.json` (прогін з
дефектом перевірки) і `precheck-gw0-fixed.json`.

## Дизайн наступного screening

Обидва плеча отримали однаковий скрипт (`verify-refactor.sh` v1.1.0,
SHA-256 `6686117bc673ed9f58cc63433ce34a2ce2cd68f47965238853ee044785277876`) та
однаковий inventory-рядок про нього. Відрізняється лише блок gate:

- `reference` (`/tmp/go-refactor-luna-review-20260909/verification-reference`,
  SKILL.md SHA-256 `48a0ba1f4ba5a19c3d70ec1e7667b42d733f6db1b18718c837f84be6e93acef3`):
  прийнятий текст «measure the starting and final production line counts»;
- `baseline` = candidate (worktree `refactor-luna-review`, SKILL.md SHA-256
  `fe8e0e0fbf9cc7a1b256bb5c1e506095713a7532973bbfd8ee8d37aeb8182f9a`):
  два визначені числа, обидві команди лічильника та вердикт за exit code.

Шаблон звіту кандидата також виправлено за P3-зауваженням попереднього рев'ю:
інструмент у Summary тепер два числа, а Verification вимагає вставити
надрукований `loc-diff`. У reference шаблон залишився попереднім.

Питання наступного screening формулюється так: чи виконує сесія вимірювання до
першої production-правки, коли інструмент названий і повертає вердикт, тоді як
у попередньому проході це не зробила жодна з 4 підтверджених candidate-сесій.

## Screening кандидата v2

Виконано двічі. Перший прогін (`screen2`) показав, що перевірка походження
працює на живих сесіях: `baseline gw0` знайшов і прочитав ту саму стару копію
`abrun-arm-260505954` (SHA-256 `b35e0092…`), що зіпсувала перший прохід, і був
позначений `SKL` та виключений. У temp-корені лежало 9 покинутих staging-дерев
попередніх прогонів (їх лишає перерваний `go run`); їх видалено, а чужі
`abrun-work-*` не торкали — там ще 31 копія навички, тому детектор лишається
потрібним.

Другий прогін (`screen3`) — фінальний: 5 входів × 2 плеча × 1 повтор,
GPT-5.6-Luna medium, Codex, seed 1, j=2, без repair. Обидва плеча отримали
однаковий prompt; до корпусного тексту додано однакову вказівку кореня skills,
бо у попередніх прогонах сесії витрачали кроки на неіснуючі `r0/`-шляхи. Це
змінює порівнянність із першим проходом, але не різницю між плечима.

| | reference | candidate |
|---|---|---|
| build / independent golden | 5/5 | 5/5 |
| прочитав власний skill | 5/5 | 4/5 |
| сторонні читання | 0/5 | 0/5 |
| запускав лічильник LOC | 0/5 | 4/4 із тих, що прочитали skill |
| виміряв обидва числа **до** першої правки | 0/5 | 2/4 |
| physical gate | 3/5 | 4/5 |
| code gate | 3/5 | 4/5 |
| mean Δphysical | +0.2 | −0.4 |
| mean Δcode | +0.2 | −1.2 |
| mean Δfuncs | +0.40 | +0.60 |

Δcode падає швидше за Δphysical у кандидата, тобто скорочення не оплачене
документацією. Єдиний вхід, де кандидат провалив обидва gate (`gw2`, +15/+10,
+3 функції), — це сесія, яка не прочитала свій skill: 4 команди, лише
`r0`-шлях, `own-skill read` = false. Тобто це не результат тексту кандидата.

Головний зсув порівняно з першим проходом: тоді 0 із 4 підтверджених
candidate-сесій виконали хоч якесь вимірювання перед правками, тепер лічильник
запускають 4 із 4, а reference не міряє LOC узагалі. Слабке місце — порядок:
дві сесії (`gw0`, `gw1`) записали baseline уже після першої правки, тобто
«starting counts» у них не стартові. Інструмент цього не бачить і не може
бачити; це наступна ітерація формулювання, а не дефект лічильника.

## Рішення

Gate не переноситься в checkout. Screening пройшов критерії build/golden,
обидва LOC gate на 4/5 і збереження документації, але «вимірювання до першої
production-правки» виконано лише в 2 із 4 підтверджених сесій, і кожен вхід має
n=1. За правилом плану наступний крок — n=3 із цим самим кандидатом плюс
окремий варіант формулювання щодо порядку кроків; лише після цього рішення про
перенесення й залежні етапи 2–4.

`*.screen2-audit.json`, `*.screen2-traces.tar.gz`, `*.screen3.json`,
`*.screen3-audit.json`, `*.screen3-traces.tar.gz`, `*.audit.py`,
`*.provenance.go.txt`, `*.provenance_test.go.txt`, `*.loc_test.go.txt`,
`*.provenance-hooks.patch`, `*.candidate-v2.patch` (усі з префіксом
