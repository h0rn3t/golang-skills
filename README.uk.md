# Agent Skills для Go

[English](README.md) | **Українська**

AI [Agent Skills](https://agentskills.io/) для написання ідіоматичного
**Go 1.27** рівня продакшену. 24 модульні скіли навчають AI-асистентів
найкращим практикам Go, узятим із:

- [Google Go Style Guide](https://google.github.io/styleguide/go/)
- [Effective Go](https://go.dev/doc/effective_go)
- [Uber Go Style Guide](https://github.com/uber-go/guide/blob/master/style.md)
- [Go Wiki CodeReviewComments](https://github.com/golang/go/wiki/CodeReviewComments)

Скіли налаштовані за
[найкращими практиками agentskills.io](https://agentskills.io/skill-creation/best-practices):
те, що агент і так знає, — пропущено; процедурні дерева рішень ведуть через
багатокрокові задачі; 69 довідкових файлів завантажуються на вимогу через
прогресивне розкриття; 10 вбудованих скриптів автоматизують типові перевірки;
5 шаблонів-ассетів забезпечують однаковий формат виводу. Плагін для Claude
Code також містить сабагента `go-verify`, який проганяє гейт перевірки,
PostToolUse-хук, що запускає `gofmt`, `go vet` та `go fix -diff` після кожної правки `.go`-файлу,
шлюз маршрутизації, який затримує першу правку Go, доки `go-code` не
завантажить `go-style-core` і скіли-власники, хук промпту, який називає
`go-code` або `go-code-refactor`, коли промпт просить роботу з Go, і хук
субагентів, який повторює цю нотатку кожному субагентові, запущеному в
Go-проєкті.

|---|---|

Старі каталоги видалено. Для ручної інсталяції скопіюйте актуальні каталоги
власників разом із references та приберіть три застарілі копії, щоб уникнути

синтаксису завантажуються за потреби.

## Вбудовані скрипти

10 скриптів автоматизують типові перевірки Go. Усі підтримують `--help`,
`--json` для структурованого виводу та осмислені коди виходу (0 = чисто,
1 = знайдено проблеми, 2 = помилка). Аналітичні скрипти підтримують `--limit`
для обмеження обсягу виводу, а скрипти, що перезаписують файли, вимагають
`--force`.

| Скрипт | Скіл | Призначення |
|--------|------|-------------|
| `verify-refactor.sh` | go-code-refactor | Зафіксувати результати перевірок до/після і порівняти їх, щоб довести незмінність поведінки |
| `check-debt.sh` | go-code-refactor | Зібрати маркери `Kept:` у реєстр і позначити ті, що не називають шлях виправлення |
| `pre-review.sh` | go-code-review | Запустити gofmt + go vet + golangci-lint перед рев'ю |
| `check-naming.sh` | go-naming | Виявити SCREAMING_SNAKE, гетери з префіксом Get, погані імена пакетів |
| `check-docs.sh` | go-documentation | Знайти експортовані символи без doc-коментарів |
| `check-errors.sh` | go-error-handling | Відловити голі return, порівняння помилок рядками, log-and-return |
| `check-interface-compliance.sh` | go-interfaces | Знайти інтерфейси без перевірки на етапі компіляції |
| `bench-compare.sh` | go-performance | Запустити бенчмарки з опційним порівнянням через benchstat |
| `setup-lint.sh` | go-linting | Згенерувати .golangci.yml з рекомендованими лінтерами |
| `gen-table-test.sh` | go-testing | Створити каркас файлу з табличним тестом |

## Вбудований агент і хук

Встановлюються разом із плагіном для Claude Code (варіант 2 нижче); `npx skills`
копіює лише скіли.

| Файл | Що робить |
|------|-----------|
| `agents/go-verify.md` | Опційний Claude-агент для запитаних перевірок: «check it builds» означає збірку, «run the gate» — повний гейт. Повертає знахідки й недоступні перевірки; `INCOMPLETE` означає, що обов'язкових доказів бракує. Звичайні перевірки виконуються в основному потоці, якщо користувач або середовище не задає делегування |
| `hooks/go-vet-on-edit.sh` | PostToolUse-хук: після кожного `Edit`/`Write` `.go`-файлу запускає `gofmt -l`, `go vet` і `go fix -diff` (лише звіт) для його пакета й віддає знахідки агентові. Мовчить, коли все чисто; ніколи не блокує правку |
| `hooks/go-prompt-routing.sh` | UserPromptSubmit-хук: коли промпт просить роботу з Go — називає Go, `.go`-файл чи `go.mod`, або надісланий з каталогу з Go-кодом і називає функцію, пакет, хендлер чи тест — додає в контекст моделі одну нотатку з назвою роутера, який треба завантажити до першої правки: `go-code-refactor` для слів refactor, clean up, simplify, `go-code` для решти. Один раз на скіл на сесію; мовчить, якщо сесія вже завантажила скіл, промпт сам викликає go-* скіл або не містить дієслова роботи. Ніколи не блокує |
| `hooks/go-code-routing.sh` | Шлюз маршрутизації для роутера `go-code`. PostToolUse на `Skill` і `Read` записує, які go-* скіли сесія завантажила; PreToolUse на `Edit`/`Write` `.go`-файлу в сесії, що завантажила `go-code`, блокує правку (exit 2), доки не завантажено `go-style-core` і власників, на яких вказує вміст правки, і називає їх. Кожен скіл називається один раз за сесію, тож повтор завжди проходить. Мовчить у сесіях, які не вантажили `go-code` |
| `hooks/go-subagent-routing.sh` | SubagentStart-хук: субагент стартує з порожнім контекстом, тож коли робочий каталог містить Go, хук додає одну нотатку з назвою `go-code`, або `go-code-refactor` для рефакторингу, які треба завантажити до першої правки. Спрацьовує для кожного субагента; пропускає власного агента плагіна `go-verify`; ніколи не блокує |

Спільні інструкції підтримують Claude та GPT-6 без окремої гілки для моделі.
`go-style-core` визначає пріоритет запиту користувача, повідомлення про поступ,
довжину звіту й делегування за правилами середовища. `go-linting` вимагає
фактичних результатів і добирає перевірки за обсягом роботи. Правила враховують
[рекомендації OpenAI для GPT-6 Astra](https://developers.openai.com/api/docs/guides/latest-model/gpt-6-astra.md#prompting-best-practices).
Див. [рев'ю та межі перевірки](docs/CROSS_MODEL_REVIEW.md).

### Codex

Встановіть каталоги скілів у `.agents/skills/` проєкту або
`~/.agents/skills/` користувача згідно з
[офіційною документацією](https://learn.chatgpt.com/docs/build-skills).
Викликайте `$go-code <завдання>` або окремий скіл, наприклад `$go-error-handling`.
Повний пакет забезпечує всі посилання маршрутизатора. За часткового встановлення
він повідомляє про відсутні настанови та продовжує з доступними скілами.
Шляхи скриптів відраховуються від встановленого скіла; перевіряється цільовий
проєкт. У Codex немає ні інструмента Skill, ні хуків: `go-code` каже йому
читати кожен вибраний сусідній `SKILL.md` напряму до першої правки, а без
результатів хука вибрані перевірки запускаються напряму.

## Встановлення

### Варіант 1. npx skills (рекомендовано)

Найпростіший спосіб встановити в **будь-який** AI-агент. Підтримуються Cursor,
Codex, OpenCode, Cline, GitHub Copilot, Windsurf, Roo Code та [25+ інших
агентів](https://github.com/vercel-labs/skills#supported-agents).

```bash
# усі 24 скіли одразу
npx skills add h0rn3t/golang-skills --all

# або вибірково — лише потрібні скіли
npx skills add h0rn3t/golang-skills go-error-handling go-testing
```

Команду запускають у корені проєкту: скіли ставляться в каталог поточного
агента (наприклад, `.cursor/rules/`, `.github/copilot/skills/`).

### Варіант 2. Claude Code (плагін)

```bash
# додати маркетплейс (один раз)
/plugin marketplace add h0rn3t/golang-skills

# встановити скіли
/plugin install golang-skills@golang-skills
```

Перевірити встановлення: `/plugin` — плагін `golang-skills` має бути зі
статусом enabled. Скіли підхоплюються автоматично, коли ви працюєте з Go-кодом.

Оновлення та видалення:

```bash
/plugin marketplace update golang-skills
/plugin uninstall golang-skills@golang-skills
```

### Варіант 3. Ручне встановлення (Claude Code / Agent Skills)

Підходить, якщо потрібні лише окремі скіли або немає доступу до маркетплейсу.

```bash
git clone https://github.com/h0rn3t/golang-skills.git
cd golang-skills

# усі скіли, глобально для користувача
cp -R skills/go-* ~/.claude/skills/

# або лише для одного проєкту
cp -R skills/go-* /шлях/до/проєкту/.claude/skills/

# або один конкретний скіл
cp -R skills/go-error-handling ~/.claude/skills/
```

Кожен скіл — це самодостатній каталог: `SKILL.md` плюс `references/`,
`scripts/`, `assets/`. Копіюйте каталог цілком, інакше зламаються
відносні посилання всередині `SKILL.md`.

Скрипти мають бути виконуваними:

```bash
chmod +x ~/.claude/skills/go-*/scripts/*.sh
```

Перевірка: у Claude Code виконайте `/context` або попросіть агента
«використай скіл go-naming» — скіл має знайтися. Видалення — просто
`rm -rf ~/.claude/skills/go-*`.

### Варіант 4. Cursor (нативне віддалене правило)

1. Відкрийте **Cursor Settings** (Cmd+Shift+J на Mac, Ctrl+Shift+J на Windows/Linux)
2. Перейдіть до **Rules** → **Add Rule** → **Remote Rule (Github)**
3. Введіть: `https://github.com/h0rn3t/golang-skills`

### Встановлення конкретної версії

Кожен реліз — це git-тег (`v1.9.0`). Жоден із варіантів вище не приймає версію:
`npx skills add` і `/plugin marketplace add h0rn3t/golang-skills` слідують за
типовою гілкою, тобто завжди дають найновіший реліз. Щоб зафіксувати версію,
встановлюйте з checkout за тегом:

```bash
git clone --branch v1.9.0 --depth 1 https://github.com/h0rn3t/golang-skills.git
cd golang-skills

# ручне встановлення з цього checkout
cp -R skills/go-* ~/.claude/skills/

# або зареєструйте сам checkout як marketplace у Claude Code
/plugin marketplace add /абсолютний/шлях/до/golang-skills
/plugin install golang-skills@golang-skills
```

Тег не рухається, тому й скіли не рухаються: ніщо не зміниться, доки ви не
склонуєте інший. Корисні команди:

```bash
# усі випущені версії
git ls-remote --tags https://github.com/h0rn3t/golang-skills.git

# яка версія у checkout або встановленої копії
grep '"version"' .claude-plugin/plugin.json

# перевести встановлений плагін на найновіший реліз
/plugin marketplace update golang-skills
```

## Як це працює

Скіли відповідають [відкритому стандарту Agent Skills](https://agentskills.io/),
який працює в різних AI-інструментах для роботи з кодом. Коли ви пишете
Go-код:

1. **Автоматична активація**: агент завантажує релевантні скіли за контекстом
   (наприклад, `go-naming`, коли ви пишете нову функцію)
2. **Процедурні підказки**: дерева рішень і покрокові процедури для
   багатокрокових задач — рев'ю коду, вибір стратегії обробки помилок
3. **Прогресивне розкриття**: базові правила завантажуються одразу; 61
   довідковий файл — на вимогу, коли виникає конкретна ситуація
4. **Автоматизація**: 10 вбудованих скриптів беруть на себе рутинні перевірки,
   щоб агент займався змістовними рішеннями
5. **Умовні перехресні посилання**: скіли посилаються один на одного з умовами
   «коли», щоб не тягнути зайвий контекст
6. **Володіння правилами**: `docs/RULE_OWNERSHIP.md` тримає дубльовані настанови
   поза скілами, які ними не володіють
7. **Гейт перевірки**: `go-linting` володіє єдиним придатним до перевірки
   визначенням «готово» — `gofmt`, `go vet`, `go test -race`, `go fix -diff`,
   `golangci-lint`, `govulncheck` — до якого звертаються решта скілів замість
   власних вигаданих критеріїв
8. **Правила, які перевіряє лінтер**: базовий `.golangci.yml` у `go-linting`
   вмикає лінтери, що перевіряють те, чого навчають скіли — `depguard` для
   драбини залежностей, `sloglint`, `errorlint`, `errname`, `noctx`,
   `rowserrcheck`, `perfsprint`, `usetesting`, `godot` — тож дрейф ловить гейт,
   а не рев'юер

## Запуск eval'ів

`evals/evals.json` містить 106 eval'ів на тригери (чи спрацьовує потрібний скіл
на запит?) і 61 eval'ів на якість (чи відповідь задовольняє кожне твердження?).
Go-тести в `evals/` перевіряють їхню схему на кожному пуші; прогін через модель
опційний, бо коштує токенів:

```bash
cd evals
go run ./cmd/evalrun -set validation -kind all -j 2 -out evals-results.json
```

Раннер завантажує скіли з робочої копії через `claude --plugin-dir`, виконує
кожен запит у порожньому тимчасовому каталозі з набором інструментів, зведеним
до `Skill` (плюс інструменти лише для читання в якісних eval'ах), фіксує, які
`go-*` скіли модель викликала на кожен тригерний запит, доводить кожен якісний
запит до кінця, а другу модель просить оцінити відповідь за твердженнями eval'а.
Провалений тригерний eval означає, що модель прочитала описи скілів і не обрала
очікуваний — сигнал доопрацювати саме опис. У CI запустіть workflow `Validate Skills` вручну з прапорцем
**run_evals**; потрібен секрет `ANTHROPIC_API_KEY`.

Автоматичний runner працює лише з Claude; `-model` не перемикає провайдера.
Сценарії 22–27 перевіряють обсяг роботи, недоступні перевірки, повторне
використання результатів, явні вимоги, characterization-тести та встановлення
без плагіна. Для GPT-6/Codex запускайте ці запити в нових сесіях зі скілами з
поточного checkout і зберігайте відповіді окремо. [Рев'ю](docs/CROSS_MODEL_REVIEW.md)
відділяє такі проби поведінки від повного порівняльного бенчмарку.

Використано останній доступний контрольний прогін для кожної пари модель +
інструмент + тип роботи за `finished` у JSON (7–11 вересня 2026 за місцевим часом)
з одним винятком: новіший прогін із меншою кількістю повторів не витісняє
прогін із більшою. Клітинку рефакторингу для Sonnet задає контроль від
10 вересня на medium, n = 5 на фікстуру й плече, на релізі 1.7.0; клітинку
нового коду — прогін 11 вересня на три плечі, n = 5, на робочому дереві
після 1.7.0, чиє плече `baseline` несе правки для нового коду й переналаштування
Plain Code, описані в changelog; прогони з одним повторенням їх лише уточнюють.
Рівень зусиль — частина
ідентичності контролю: та сама модель і те саме дерево плагіна того самого дня
дали різницю корпусу −9.7 на medium (n = 5) і −1.8 на high (n = 1), тож рядок,
прочитаний упоперек рівнів зусиль, прочитано неправильно.
Новіший тест частини корпусу не означає, що перевірено весь корпус. У прогонах
із варіантами порівнюється **baseline із відсутністю скілів**, а не найкращий
варіант. Старі результати й детальні числа залишаються у звітах за посиланнями.

**Рівень зусиль на Opus 5.** Запускайте плагін на Opus 5 з `--effort medium`:
кожну клітинку Opus 5 вище виміряно саме там, а настанови Anthropic з міграції
на Claude Opus 5 називають `low` і `medium` головним важелем вартості, тоді як
`high` є типовим значенням API. [Прогін від 2026-09-12](docs/evidence/2026-09-12-go-implement-effort-sweep-opus-5.md)
запустив контроль без скілів і руку зі скілами на `low` і `high` для трьох
задач нового коду при n = 5: ефект коректності на `HEAD` однаковий на кожному
рівні, ефект розміру є лише на `high`, а множник вартості найгірший на `low`
(5.7×), бо текст скілів — фіксована плата поверх дешевшої сесії. `medium`
лишається рекомендованим рівнем: виміряний для кожної клітинки і посередині
за вартістю. Пара Sonnet 5 вище, −9.7 рядка на medium і −1.8 на high на
одному дереві в один день, показує, чому порівняння тримається лише в межах
одного рівня зусиль.

**Вартість завантаження.** На трейсах Opus 5 medium від 2026-09-11
маршрутизована сесія імплементації вантажить близько 23K токенів тексту скілів
за три-чотири ходи `Skill`; записаний у кеш один раз і перечитаний на кожному
наступному виклику, цей текст дає близько 37% вартості сесії. Реліз 1.12.0
вантажить owners одним повідомленням після `go-code`, прибирає три розділи
`go-style-core`, які модель і так знає, та приписи про перевірку в трьох скілах,
і стискає кожен розділ Related Skills. Виміряно на `feed`, Sonnet 5 medium, n=5,
reference проти baseline: golden 5/5 в обох плечах, `go-style-core` 2867 → 2335
токенів при завантаженні, cache writes 40.9K → 35.9K, $0.299 → $0.275 на сесію
([звіт](docs/evidence/2026-09-11-go-implement-load-cuts-feed-n5-sonnet-5-medium.md)).
На Opus 5 reference-сесія `gateway` вантажила шість owners по одному за хід, де
1.12.0 вантажить їх одним повідомленням: 16 API-викликів проти 10
([smoke, n=1](docs/evidence/2026-09-11-go-implement-load-cuts-smoke-opus-5-medium.md);
[smoke Sonnet 5](docs/evidence/2026-09-11-go-implement-load-cuts-smoke-sonnet-5-medium.md)).
Таблиця вище без змін: ці прогони мають n=1 або не мають плеча без скілів.

[HTTP-експерименти Sonnet 5](docs/evidence/2026-09-08-sonnet-http-compact.md)
також виявили блокування читання довідників у стенді Claude. Оновлення
9 вересня виправляє стенд і додає компактний HTTP-скіл зі збереженими
клієнтськими правилами та перевірками коректності. Вплив цієї комбінації
на вартість ще не виміряно.

Клітинка «новий код» для GPT-5.6-Luna — з триплечового прогону: без скілів,
дерево скілів до правки від 2026-09-08 і дерево після неї. Тому вона відділяє
те, що робить плагін, від того, що зробила правка. Правка не змінює ні
коректності (20/20 проходжень скритого тесту в усіх трьох плечах), ні обсягу
(+0.70 рядка на корпусі, p = 0.94).

Що показало третє плече — це ціна, яка лишається напрямком: на `gateway` кожне
виміряне дерево зі скілами пише більше хелперів на сесію, ніж модель без скілів
(2.40…3.20 проти 1.40), і не купує за них ні рядків, ні гілок.
[Прогін-перевірка лише на `gateway`](docs/evidence/2026-09-08-go-new-code-gateway-gpt-5.6-luna-codex.uk.md)
переміряв побайтово те саме плече і дав 4.40 хелпера там, де перший прогін дав
1.80: розкид на цій фікстурі — 0…7 на сесію, і для різниці у два хелпери
потрібно близько n=20 на плече. Тож цей розрив варто читати як невирішений, а
будь-який окремий результат по хелперах на `gateway` при n=5 — у будь-який бік —
як одну витяжку з цього розкиду.

«Допомагає» тут означає спостережуване зменшення зайвого коду або хелперів
без провалів наявних перевірок; читабельність не оцінювали окремим сліпим рев'ю.
Вибірки невеликі: 3–10 повторів на задачу. «Користі не доведено» не означає
«скіл завжди шкодить». Вартість — співвідношення записаних USD за весь прогін,
а не економія output-токенів. У прогоні Sonnet 5 на medium `dispatch` і
`report` переживають поправку Бонферроні на чотири порівняння корпусу;
`pricing` після неї лишається дослідницьким, а `store` — нічия.
