# Этап 2 — feedback repair, GPT-5.6-Luna (medium) на Codex

2026-09-09. Десять сохранённых проблемных outputs прогона 5×5, по одной repair-
сессии на каждом из двух плеч feedback-а: 20 сессий. **Точный feedback починил
10/10, generic repair — 1/10, exact paired sign test p = 0.00391. Этап 2
пройден с большим отрывом.**

- Починено (LOC ≤ стартового **и** golden зелёный): **10/10** candidate против
  **1/10** control.
- Новых golden failures: **0** candidate против **1** control.
- Регрессию контракта `nil → null` candidate исправил, control — нет.
- Ни одного чистого откката: все десять результатов отличаются от исходной
  реализации, то есть это починки, а не восстановление стартовой версии.
- Заявленное моделью число строк совпало с харнессом в **10/10** candidate.

## Дизайн

Входы — те самые десять проблемных outputs плеча `concision-gate` прогона 5×5,
отобранные из его raw JSON: девять с `Δlines > 0` (роста `+2, +2, +4, +5, +5,
+12, +16, +22, +33`) и один с регрессией wire shape (`gateway-concision-0`
rep 3, `Δlines −5`, golden провален). Каждый разложен как фикстура
refactor-корпуса `rp0`…`rp9`; `rp8` совпал с примером плана дословно.

| `rp1` | concision-2 rep 1 | 127 | 149 | +22 | зелёный |

Предпосылки проверены до запуска: все десять компилируются, девять проходят
hidden golden, `rp0` падает ровно на `GET /accounts = 200 "null", want 200 []`.
Число физических строк файла совпало с `after.lines` прогона 5×5 во всех десяти
случаях — то есть сохранённый `output` есть production-источник и ничего больше.

Плечи:

- `control` — generic repair одним prompt-ом на все десять фикстур:
  `Re-review the Go package in ./%s for concision while preserving behavior.`
- `candidate` — десять отдельных инвокаций, каждая со своими измеренными
  числами. Десять, а не одна, потому что `-prompt` в `abrun` — один шаблон на
  инвокацию и per-fixture числа в него не подставить.

**Отступление от плана, осознанное.** Пример prompt-а в плане совмещает рост
`+16` и contract failure в одном тексте, но такого прогона в реальности нет:
`rp8` вырос на +16 при зелёном golden, `rp0` сломал контракт, сократившись.
Поэтому каждая фикстура получила feedback, истинный для неё: девять — «Gate:
FAIL, growth +N», `rp0` — «Gate: PASS on line count» плюс строку contract
failure. Сообщить `rp8` о несуществующем падении контракта означало бы мерить
реакцию на ложный факт.

## Запуск

- Runner: Codex CLI 0.153.4; model `gpt-5.6-luna`; effort `medium`.
- 10 фикстур × 2 плеча × 1 повтор = 20 сессий; seed 1; timeout 10 минут;
  `-keep`. Control `j=4`; candidate по пять инвокаций параллельно.
- Plugin SHA-256 **обоих** плеч:
  `5509f19786639774c1bc6e6bc822d5f8fd7ae56efab7836976fbff63a6b89148` —
  плагин держался постоянным, менялся только feedback.
- Ни одного `leaked` прогона из 20: ни одна сессия не дотянулась до
  репозитория, где лежит hidden golden.

## Почему generic repair провалился

### Определение LOC оказалось несущим

`rp5` — самый ясный случай. Файл содержит **138 физических строк**; строк без
пустых и комментариев — **101**. Control-сессия ответила «Lean already… No safe
concision changes identified… Production code: 101 lines» и не изменила ничего.

Модель не выдумала число: она выбрала другую, вполне защитимую конвенцию
подсчёта и по ней была права. Харнесс при этом фиксирует 138 и рост +12.
Плечи не расходились в оценке кода — они считали разные вещи.

Это retroactively объясняет часть результата 5×5: гейт требует «no more
production lines», не определяя, что такое строка, поэтому модель может
удовлетворить собственный гейт, пока харнесс пишет рост. Пункт 2 этапа 0
(«зафиксировать определение production LOC») до этого прогона выглядел
гигиеной; теперь под ним есть доказательство поведения модели.

Candidate-плечо называет оба числа в терминах харнесса — и заявленное моделью
итоговое число совпало с харнессом в **10/10** прогонов.

### Generic repair сам ломает поведение

Control на `rp1` сократил 149 → 142 и внёс регрессию, которой на входе не было:

```text
--- FAIL: TestStatusCodes/post_to_list  POST /accounts = 200, want 405
--- FAIL: TestStatusCodes/head_to_list  HEAD /accounts = 200, want 405
```

Это ровно тот класс отказа, который Stop-критерий этапа 2 запрещает, — и он
случился в control, не в candidate.

## Проверка качества починок

Ни один candidate-результат не идентичен исходной реализации, хотя prompt прямо
разрешал «restore the starting version». Все десять — переписанный код.

`rp7`, самая агрессивная починка (159 → 124), сохраняет: заголовок `Allow` на
405, все четыре таймаута, `MaxHeaderBytes` и `MaxHeaderValueCount`, 400 с
названным параметром, `Content-Type`, `strings.CutPrefix`, именованные хелперы
`accountIDFromPath`/`accountsForQuery`/`findAccount`. Guard clauses и ранние
возвраты. Это не code golf.

`rp0` — единственный, кто **вырос** относительно входа (130 → 133): починка
`nil → []` требует кода. Гейт по строкам на входе был PASS, ломался контракт, и
результат остался в пределах старта (133 ≤ 135). Прямой аргумент к этапу 4:
безусловный zero-growth гейт запретил бы эту починку.

## Стоимость

Candidate — 8.4 команды на сессию против 13.8 у control. Codex не отдаёт
стоимость в долларах, так что это единственный доступный прокси. Точный
feedback вышел и результативнее, и дешевле.

## Go-критерии

| Критерий | Результат |
|---|---|
| Candidate исправляет минимум 8/10 | ✓ **10/10** |
| Не создаёт новых golden failures | ✓ **0** (control — 1) |
| Заметно превосходит generic repair | ✓ 10/10 против 1/10, p = 0.00391 |

Stop-критерии не сработали: feedback не хуже control, и после repair не осталось
ни одной новой behavioral regression.

## Чего этот прогон не показывает

Плечи различаются **содержанием информации**, а не формулировкой. Candidate
получает измеренные числа и текст падения контракта; control не получает
ничего. Поэтому результат **не переносится в правку скилла**: никакой текст в
`SKILL.md` не может сообщить модели измеренный LOC её собственного результата.
Это может только харнесс или петля — что и проверяет этап 3.

Прочие ограничения: `n=10` по одному повтору, один seed; все входы —
производные одной фикстуры `gateway`, поэтому обобщаемость проверяет этап 6.
`rp7` в финальном сообщении заметил «No contract test is present in the
workspace», то есть вывел существование скрытого теста; утечки при этом не
было — guard `leaked` чист во всех 20 прогонах.

## Решение

Этап 2 пройден. Переходить к этапу 3 (автоматический однократный repair loop,
30 сессий) допустимо, и именно он решает практический вопрос: даёт ли петля
`измерить → вернуть точное расхождение → один repair-turn` тот же эффект без
человека, который вручную собирает feedback.

Из этого прогона в репозиторий переносится **не текст prompt-а, а определение**:
любой feedback о строках обязан называть конвенцию подсчёта, потому что
несогласованность конвенций — а не нежелание модели — объясняет как минимум
один из десяти провалов generic repair и часть роста в прогоне 5×5.
