# Огляд prompt guides для Go-скілів — 2026-09-08

Переглянуто офіційні джерела та поточне дерево на базі `0aca2fe`.
Зміни обмежено `go-code-refactor` і двома його references: прибрано
суперечливі вимоги до області модернізації та завершення дедуплікації.
Це уточнення інструкцій, а не доведене покращення результатів п'яти моделей.

[Загальні поради xAI для Grok у Foundry](https://docs.x.ai/developers/community/microsoft-foundry)

Налаштування effort, API caching, ліміти делегації та вибір моделі залишаються
в runner/host. Універсального значення effort з цих джерел не випливає.
Рекомендації Opus прибрати зайві перевірки не скасовують обов'язковий gate
репозиторію або перевірки збереження поведінки.

## Конкретні зміни

- [Scope mechanical modernization](../skills/go-code-refactor/SKILL.md#3-scope-mechanical-modernization):
  попередній рецепт безумовно пропонував `go fix ./...`, хоча `go-style-core`
  уже обмежував модернізацію задачею. Тепер preview має область пакетів,
  застосування — лише дозволені зміни. Для однієї функції сторонні hunks
  залишаються незастосованими, зокрема в тому самому файлі.
- [Remove Duplication to the End](../skills/go-code-refactor/SKILL.md#remove-duplication-to-the-end):
  повторювана політика або обчислення має одне представлення, але однакові
  числа не роблять різні політики спільними. Критерій завершення враховує
  зв'язування незалежних правил і непрямі виклики.
- [PLAYBOOK](../skills/go-code-refactor/references/PLAYBOOK.md#duplication-that-differs-only-in-values):
  збережено приклад спільної таблиці зон; уточнено, що окремі accessors
  зберігають власні помилки. Прибрано повтор абсолютної вимоги literal-once.
- [MODERNIZATION](../skills/go-code-refactor/references/MODERNIZATION.md#start-with-go-fix):
  область застосування має одного власника замість другого безумовного рецепта.
- [Quality evals 45–47](../evals/evals.json): function-only refactor,
  незалежні політики з однаковими числами, справді спільна політика зон.
  Нові випадки належать до `train`: їх використано для розробки цієї правки.

## Попередні вимірювання і межі висновків

Поточні звіти вже показують, чому не слід переписувати весь пакет за гайдами:
[Sonnet 5 refactor](evidence/2026-09-08-go-refactor-control-sonnet-5.uk.md)
і [Sonnet 5 implement](evidence/2026-09-08-go-implement-control-sonnet-5.uk.md)
мають різні напрямки за розміром коду та не ізолюють окремі правила.
[Проба router на GPT-5.6 Luna](evidence/2026-09-08-go-code-contract-gateway-gpt-5.6-luna-opencode.uk.md)
не довела покращення маршрутизації за n=3.
Ці історичні прогони не запускали повторно й не видавали за перевірку нової правки.

Перша незалежна проба поточного скіла вже обрала правильну поведінку в обох
сценаріях: вузька модернізація та незалежні політики. Отже, зафіксовано
суперечність тексту, але не відтворено помилку моделі. Правка усуває потребу
розв'язувати цю суперечність. Скорочення коду чи вартості не встановлено.

  Це підтвердження потрібних рішень у цих прикладах, а не приріст якості.
- `quick_validate.py skills/go-code-refactor`, `agentskills-validate@1.0.1`,
  перевірка відносних посилань і `git diff --check` — PASS.
- `go test -count=1 ./...` у `evals` — FAIL через дві попередні проблеми:
  `TestLongReferenceTOCs` (`PLAYBOOK`: 393 рядки до, 391 після при ліміті 300)
  та `TestFrontmatterDescriptionsInvariant/go-code` (застаріле очікування опису).
  Обидві відтворено на архіві `0aca2fe`; ці тести не послаблювали.
- Решта тестів поточного дерева, включно зі схемою eval-ів, лічильниками
  README і тестами `abrun`, пройшла. Початковий запуск обрав старий Homebrew
  linter; явний PATH до вже встановленого `golangci-lint` 2.13.2, зібраного
  Go 1.27.1, усунув цю помилку оточення. Конфігурацію користувача не змінювали.
- Одночасний повний прогін архіву мав додатковий `mktemp: File exists` у
  `BenchCompare`; лог збережено. У поточному дереві цей тест пройшов.

Сумарно три файли інструкцій скорочено на 11 рядків. Це розмір текстової
правки, не вимірювання токенів чи розміру згенерованого Go-коду.

Це короткі симуляції рішень у незалежних контекстах поточної Codex-сесії,
а не виконання рефакторингу на п'яти моделях і не автоматичний запуск
`evalrun`. Assertions оцінює основний агент; evaluator отримує сценарії без
очікуваних відповідей. Сценарії baseline і candidate семантично зіставні,
але формулювання не побайтово однакові; позитивний випадок зон є лише в candidate.

Для перевірки ефекту потрібне порівняння `reference` (`0aca2fe`) і нового
`baseline` на тих самих fixtures, runner, моделі й effort. Зберігати результати
коректності, код і diff кожної сесії, завантажені скіли, токени, час та вартість;
порівнювати весь код із call sites. Почати з `pricing`, `report`, `gateway`
та n≥10 на плече, потім розширювати за результатами. Навіть такий розмір
вибірки сам собою не гарантує статистичної потужності.
